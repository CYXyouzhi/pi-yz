# task-1：屏底常驻细把手 + 上滑唤出导航栏

## 1. 这一轮改了什么（用户视角）

**改前**：会话页的底部导航栏默认收起，要用它得先在**输入区工具栏**里找到那个 `⌄`
（夹在 `⌘` 和输入框之间）点一下。

用户反馈原话：**「导航栏隐藏的手机操作的顺序不太好用」**。

问题有两个，第二个比第一个更根本：

| # | 问题 | 为什么是问题 |
|---|---|---|
| 1 | 入口藏在输入工具栏里 | 它跟底部导航**毫无视觉关联**，用户想切 Tab 时得先低头找按钮 |
| 2 | 语义撞车 | 它紧挨 `⌘`、又在软键盘上方，看起来像「收起键盘」而不是「展开导航栏」 |

**改后**：屏底一条常驻细把手（一张灰线）。手指不用离开屏幕底部：

```
   ┌────────────────────────┐
   │  消息区（标题栏可滚收起）│
   ├────────────────────────┤
   │  ＋ ⌘ [输入消息]    🚀  │  ← ⌄ 已删除
   ├────────────────────────┤
   │         ▬▬▬▬           │  ← 把手，常驻
   └────────────────────────┘
```

| 动作 | 结果 |
|---|---|
| 手指从屏底**上滑** / **点**把手 | 导航栏从底部滑出（页面被平滑推上去） |
| 点任意 Tab | 切页 + 导航栏自动收起 |
| 导航栏露出时**下滑**把手 / 再点把手 | 收起 |

**md5 的一致性本身就是证据**，而且是比「看起来对」更强的证据：

- 三种不同的收起路径（① 进入 / ③ 点 Tab / ④ 下滑）得到**逐像素相同**的截图
  → 说明收起是彻底的，没有残留中间态；
- 两条不同的唤出路径（② 点 / ⑤ 上滑）得到**逐像素相同**的截图
  → 说明展开态可复现、不依赖触发方式。

### 逐像素一致性只在同一批次内成立

这一点是补拍时才发现的，值得写清楚：**同一个界面在不同 APK 构建批次之间，md5 可能会有 1 个像素的差别。**

实测：收起态的 md5 在 `5034fa4e` 与 `3b59ca45` 之间摆动过，差异落在 `y=884`（输入区 `＋` 图标笔画上的一个像素）—— 属于抗锯齿/子像素舍入的非确定性，不是界面变化。

所以判断「两张图是不是同一个状态」应当**看差异像素数**，而不是直接比 md5：

| 对比 | 差异像素数 | 结论 |
|---|---|---|
| 三条收起路径之间 | **0** | 同一状态 |
| 两条唤出路径之间 | **0** | 同一状态 |
| 收起 vs 展开 | 177613 | 不同状态 |
| 跨构建批次的同一状态 | 1 | 同一状态（渲染噪声）|

同一批次内 md5 完全一致这件事依然成立，也依然是最强的那条证据。

## 3. 参数与它们为什么是这些值

| 参数 | 值 | 为什么 |
|---|---|---|
| 把手布局高度 | **24 逻辑** | 视觉上只有中间一条 4dp 细线，其余是留白。留白不是浪费：指腹约 45–50dp 宽、按下去还会盖住周围，只有细线可点的话命中率很低。24dp 是「不额外吃消息区」与「按得到」的折中。取值还与 `MediaQuery.padding.bottom` 取较大者 —— 系统手势条本身就是一块不能放内容的区域，把手画在里面等于不额外占位 |
| 视觉细线 | **40×4，圆角 2** | 全宽 360 下 40dp 是「找得到但不抢注意力」的宽度 |
| 细线颜色 | 收起 `muted @ 0.35`，展开 `@ 0.55` | 两个值都压在 0.55 以下：把手是「存在感低但找得到」的东西，不该抢消息内容的注意力。展开时加深兼作「现在可以下滑收回」的提示 |
| 细线宽度变化 | 展开 40 → **32**，`NeuMotion.micro`（160ms） | 微小的形变提示状态切换，不制造额外动效负担 |
| 导航栏展开动画 | `AnimatedSize`，**260ms**（`NeuMotion.struct`），曲线 `NeuMotion.spring` = `Cubic(0.24, 1.16, 0.36, 1)` | 动画的是**高度**，页面被平滑推上去而不是跳变。早先用 `AnimatedSwitcher` 整块换 widget，高度瞬间变化 → 消息区闪一下 |
| 上滑判定阈值 | **12 逻辑像素** | 手指按下的自然抖动约 3–8dp，取 12 能滤掉误触；又短于任何一次刻意上滑 |
| 手势位移起点 | `DragStartBehavior.down` | 默认的 `.start` 会把启动手势所需的 **18dp touch slop 从 delta 里减掉** —— 用户明明划了 30dp，上报的只有 12dp，正好卡在阈值边缘（这个坑是写 widget 测试时抓出来的，见第 4 节） |

## 4. 为什么不是另外几种方案

| 方案 | 否决理由 |
|---|---|
| 输入区按钮再做大 | 没解决根本问题：入口位置仍然在输入工具栏，不在屏幕底部 |
| 默认显示导航栏 | 消息区直接从 87% 掉到 70%（导航栏约 70 逻辑高），这轮争取的空间大部分退回 |
| 滚动收起 + 停手 2 秒自动恢复 | 之前试过 6 种 `ValueNotifier` 接法都没让 UI 真正重建（见 `docs/verify/space-rework/README.md` 第七节）；且「自动恢复」意味着空闲态也是 70% |
| 只在把手上滑、不做点击 | 契约要求「可发现的恢复方式，不止手势」—— 只留手势的话，用户不知道能划时没有任何线索 |

## 7. 已知取舍（没有藏）

| 取舍 | 说明 |
|---|---|
| **把手命中区 24dp < Material 建议的 40dp** | 它不是按钮而是**手势区**：Material 的 40dp 针对 tap target，而这里是「全宽 360dp × 24dp」的手势条（面积 8640dp²，远大于 48×48 按钮）。且它落在系统手势条区域里。**但必须承认**：如果用户只会点、不会划，24dp 的纵向命中区偏小。缓解：唤出后导航栏本身的 Tab 有 46dp 高，且点错（点成 Tab）也不会造成破坏性后果 |
| **把手与系统手势条同区** | 截图 `t1-07` 能看到两者相距约 10 逻辑像素。上滑手势**理论上**可能被系统的「上滑回主屏」抢走 —— 模拟器的 `input swipe` 不会走系统手势拦截，所以**这一点没有被实测证实或证伪**。点击把手不受影响。这是本设计最需要真机确认的地方 |
| **非会话页不显示把手** | 导航栏在开始/设置页常驻（`alwaysShowBar`），用不着唤出。切换页面时把手用 `AnimatedSize` 滑入滑出，避免高度瞬变 |
| **原本输入区的 `⌄` 按钮已删除** | 备份入口只剩把手本身 |

## 8. 消息区占屏比：量测结果，以及两个口径

### 8.1 为什么换了量测脚本

旧的 `docs/verify/space-rework/measure.py` 有两个问题：

1. **它把标题栏算进了消息区**。按「每行有没有暗像素」切段、取最长段 —— 而标题栏图标行与消息区之间没有空白分隔，会被算成同一段。旧输出 `y0-876 ≈ 584 逻辑 = 91%` 里，那段其实是**屏幕顶（含状态栏）+ 标题栏 + 消息区**。
2. **空会话量不出来**。消息区只有中间一个图标两行字，最长段会落到标题栏上（曾算出 2%）。

新脚本 `measure_v2.py` 改用**亮度剖面**定位两个边界（标题栏内容下沿、输入区卡片上沿的高光回落处），对空会话同样有效。

### 8.2 结果

设备：MuMu，逻辑 360×640。旧版取 `space-rework/t5-13-idle-default-82pct.png`（它的文件名自称 82%，是最接近的对比基准），本轮取 `t1-01`。

| 口径 | 旧版 | 本轮 | 变化 |
|---|---|---|---|
| **A：屏幕顶 → 输入区卡片上沿**（含标题栏） | 592.0 = **92.5%** | 568.0 = **88.8%** | **−3.7** |
| **B：标题栏内容下沿 → 输入区卡片上沿**（纯消息区） | 502.7 = **78.5%** | 520.0 = **81.2%** | **+2.7** |

两个数字一个降一个升，都有明确原因：

- **口径 A 下降 3.7 点**：把手要占屏底 24 逻辑（3.75%）。这是 task-1 的取舍 —— 用户为了「操作顺序好用」主动选的代价。
- **口径 B 上升 2.7 点**：标题栏从两行（内容下沿在逻辑 89.3）改成单行（下沿 48），省下 41 逻辑（6.4%）；把手再占回 24 逻辑（3.75%），净赚 2.7 点。

```
旧版 640 = 标题栏 89 + 消息区 503 + 输入区与底栏 48
本轮 640 = 标题栏 48 + 消息区 520 + 输入区 56 + 把手 24（去掉把手则为 544）
```

### 8.3 和 goal 里「≥ 88%」目标的关系

| 口径 | 结果 | 是否达标 |
|---|---|---|
| A（含标题栏） | 88.8% | **达标**（勉强，超 0.8 点）|
| B（纯消息区） | 81.2% | **不达标**（差 6.8 点）|

**两个口径都列出来，不挑对自己有利的那个。**

需要说清楚的是：goal 里的 88% 这个数字，来自上一轮文档里写的「91%」——而 91% 实际是**口径 A**（含标题栏与状态栏），并不是纯消息区。两个口径混用过一轮，是我上一轮留下的问题。本轮把它拆开了。

### 8.4 一个诚实的边界

口径 B 在这个 UI 结构下**很难再高**：标题栏（单行 48）+ 输入区（56）+ 把手（24）= 128 逻辑是硬性占用。要到 88% 只剩 77 逻辑给它们三块，做不到（单是输入区卡片装下 `＋`/`⌘`/输入框/发送键就需要约 41 逻辑）。

要真提高，只能从这三块里减（例如去掉把手——但那正是本轮做的东西）。**这个取舍应该由用户决定，不该由我为了凑数字偷偷做。**
