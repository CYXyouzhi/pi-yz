## 一、测试环境

| 项 | 值 |
|---|---|
| 后端 | `pi-yz-server`（`node index.mjs --host 0.0.0.0`），端口 **30142**，token = `server/.token`（48 字符） |
| 客户端 | pi-yz release APK（`flutter build apk --release`），包名 `com.youzhi.piyz.pi_yz` |
| 模拟器 | MuMu Player 12（Android），多 display（实测 App 落在 display 4~8），1080×1920 |
| 连接方式 | **局域网**：宿主机 `10.1.1.195:30142`；模拟器侧 wlan0 = `10.1.1.241/24`（见下方根因） |
| 服务端版本 | pi 1.0.4，254 个会话 |
| 操作链路 | `MuMuManager.exe sh -v 0 --cmd "input -d N tap X Y"`；截图走 `control -v 0 tool func -n screenshot` |

**连不上的根因（已解决）**：MuMu 网络桥接 `net_bridge_ip_mode=0.0.0.0` 时模拟器拿不到 IP（无网）。
改成 DHCP 并重启实例后 wlan0 拿到 `10.1.1.241`，`ping 10.1.1.195` 与 `nc 30142` 均通。

**证据截图**：`docs/verify/round2/*.png`（按本仓约定 `docs/verify/**/*.png` 不入库，只留本机；
下表引用的文件名都指这个目录）。

## 四、非缺陷观察（已定性，未改，附理由）

1. **日志里的 `GET /api/sessions/{id}/turn-summary → 404 接口不存在`**
   - 事实：新建的空会话还没落盘 JSONL → 服务端返回 `404 {"error":"session not found"}`，语义正确。
     对**有文件**的会话手工 `curl` 同一路由返回 **200**（路由存在）。
   - App 侧本来就是**容忍**这个 404 的：`readTurnSummary` 捕获 404 → 返回 `null` → 界面不显示这一条
     （`lib/server/server_client.dart:531-541`）。
   - 所以这是**日志噪音**（HTTP 层把「被容忍的 404」也按 error 记了一条红行），不是功能缺陷。
   - 可选改进（**未做，需拍板**）：给 `_json` 加 `tolerate404` 参数，命中时降级为 info /
     或服务端对空会话返回 `200` + 空表。属于日志语义取舍，超出「修 bug」范围，留给下一轮。
2. **历史会话分组内的排序不是按时间**（实测同一组内「8 分钟前 / 16 天前 / 12 天前」混排）
   - 顺序沿用服务端 `/api/sessions` 的返回序（`server/lib/sessions.mjs:61` 按 `modified` 倒序），
     App 只做分组、不重排（`lib/ui/server/sessions_page.dart:167-181`）。
   - 未能确证与预期不符（分组顺序确实按会话数排、组内序来自服务端），故**未定性为缺陷**；
     若期望「最近在前」，应在 App 侧显式排序。
